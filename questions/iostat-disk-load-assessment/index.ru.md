# Вопрос

Достаточно ли команды iostat -x чтобы оценить реальную нагрузку на диск?

[English version](index.md) | [Все вопросы](../../README.ru.md)

---

## Краткий ответ

Команда `iostat -x` предоставляет важные метрики дисковой подсистемы, но для полноценной оценки реальной нагрузки на диск недостаточна. Необходимо также использовать дополнительные инструменты: `iotop` для анализа процессов, `blktrace` для детальной трассировки I/O операций, мониторинг на уровне приложений и проверку конфигурации системы хранения данных.

---

## Подробное объяснение

Команда [`iostat -x`](https://linux.die.net/man/1/iostat) является важным инструментом для мониторинга производительности [дисковой подсистемы](https://ru.wikipedia.org/wiki/Жёсткий_диск), но имеет свои ограничения при оценке реальной нагрузки на [диск](https://ru.wikipedia.org/wiki/Устройство_хранения_данных).

### 1. Что показывает iostat -x

Команда `iostat -x` предоставляет расширенную [статистику](https://ru.wikipedia.org/wiki/Статистика) производительности [устройств ввода-вывода](https://ru.wikipedia.org/wiki/Ввод-вывод).

**Основные метрики:**

```bash
iostat -x 1 5  # Обновление каждую секунду, 5 итераций
```

**Ключевые показатели:**

- **`%util`**: Процент времени, когда устройство обрабатывало запросы (утилизация)
- **`await`**: Среднее время ожидания для [I/O операций](https://ru.wikipedia.org/wiki/Ввод-вывод) (в миллисекундах)
- **`r_await` / `w_await`**: Среднее время ожидания для чтения/записи отдельно
- **`avgqu-sz`**: Средний размер [очереди](https://ru.wikipedia.org/wiki/Очередь_(программирование)) запросов к устройству
- **`avgrq-sz`**: Средний размер запроса в [секторах](https://ru.wikipedia.org/wiki/Сектор_(память))
- **`r/s` и `w/s`**: Количество операций чтения и записи в секунду
- **`rkB/s` и `wkB/s`**: Скорость чтения и записи в килобайтах в секунду

### 2. Преимущества iostat -x

**Быстрая диагностика:**
- Показывает утилизацию дисков в реальном времени
- Выявляет узкие места в дисковой подсистеме
- Простота использования и интерпретации базовых метрик
- Встроен в большинство [Linux](https://ru.wikipedia.org/wiki/Linux) дистрибутивов (пакет `sysstat`)

**Пример анализа:**

```bash
Device  r/s    w/s    rkB/s    wkB/s  await  %util
sda     120.0  45.0   4800.0   1800.0  12.5   95.2
```

В этом примере:
- Высокая утилизация (95.2%) указывает на интенсивную нагрузку
- Время ожидания 12.5 мс может указывать на проблемы производительности
- Преобладание чтения над записью (120 vs 45 операций/сек)

### 3. Ограничения iostat -x

**Отсутствие детализации по процессам:**
- `iostat` показывает агрегированную статистику по устройствам
- Не показывает, какие [процессы](https://ru.wikipedia.org/wiki/Процесс_(информатика)) генерируют нагрузку
- Невозможно определить конкретные [приложения](https://ru.wikipedia.org/wiki/Прикладное_программное_обеспечение), вызывающие проблемы

**Ограниченная точность %util на современных дисках:**
- Для [SSD](https://ru.wikipedia.org/wiki/Твердотельный_накопитель) и [NVMe](https://ru.wikipedia.org/wiki/NVMe) показатель %util менее информативен
- Современные диски поддерживают [параллельные операции](https://ru.wikipedia.org/wiki/Параллельные_вычисления), %util может показывать 100% при наличии резервов
- Для массивов [RAID](https://ru.wikipedia.org/wiki/RAID) метрика может быть неточной

**Отсутствие информации о типе I/O:**
- Не различает [последовательный](https://ru.wikipedia.org/wiki/Последовательный_доступ) и [случайный](https://ru.wikipedia.org/wiki/Произвольный_доступ) доступ
- Не показывает размер блоков I/O операций детально
- Нет информации о [синхронных](https://ru.wikipedia.org/wiki/Синхронизация_(информатика)) vs [асинхронных](https://ru.wikipedia.org/wiki/Асинхронное_программирование) операциях

**Статистика на уровне блочных устройств:**
- Не учитывает кэширование на уровне [файловой системы](https://ru.wikipedia.org/wiki/Файловая_система)
- Не показывает метрики [страничного кэша](https://ru.wikipedia.org/wiki/Кэш_страниц) ядра
- Отсутствует информация о [дисковых квотах](https://ru.wikipedia.org/wiki/Дисковая_квота)

### 4. Дополнительные инструменты для полной оценки

Для комплексной оценки нагрузки на диск необходимо использовать дополнительные инструменты.

#### 4.1. iotop - Мониторинг процессов по I/O

[`iotop`](https://linux.die.net/man/1/iotop) показывает, какие процессы выполняют операции ввода-вывода.

```bash
# Установка
sudo apt-get install iotop  # Debian/Ubuntu
sudo yum install iotop      # RHEL/CentOS

# Использование
sudo iotop -o  # Показывает только процессы с I/O активностью
sudo iotop -P  # Показывает процессы вместо потоков
```

**Что показывает:**
- Скорость чтения/записи для каждого процесса
- Процент времени на операции [swap](https://ru.wikipedia.org/wiki/Подкачка_страниц)
- Приоритет I/O ([ionice](https://linux.die.net/man/1/ionice))
- [PID](https://ru.wikipedia.org/wiki/Идентификатор_процесса), пользователь, команда

#### 4.2. blktrace - Детальная трассировка I/O

[`blktrace`](https://linux.die.net/man/8/blktrace) предоставляет детальную информацию об операциях ввода-вывода на уровне [блочного слоя](https://ru.wikipedia.org/wiki/Блочное_устройство).

```bash
# Установка
sudo apt-get install blktrace

# Сбор данных
sudo blktrace -d /dev/sda -o trace

# Анализ с помощью blkparse
blkparse -i trace

# Или использовать btrace для вывода в реальном времени
sudo btrace /dev/sda
```

**Возможности:**
- Отслеживание каждой отдельной I/O операции
- Анализ задержек на разных этапах обработки запроса
- Понимание паттернов доступа (последовательный vs случайный)
- Выявление проблем с [планировщиком I/O](https://ru.wikipedia.org/wiki/Планировщик_задач)

#### 4.3. sar - Исторические данные

Команда [`sar`](https://linux.die.net/man/1/sar) из пакета `sysstat` собирает исторические данные о производительности системы.

```bash
# Статистика дисков за сегодня
sar -d

# Статистика с определенного времени
sar -d -f /var/log/sa/sa15  # Данные за 15-е число

# I/O и transfer rate статистика
sar -b 1 10  # Каждую секунду, 10 раз
```

**Преимущества:**
- Анализ исторических трендов
- Корреляция с другими системными метриками
- Выявление паттернов нагрузки во времени

#### 4.4. pidstat - Статистика по процессам

[`pidstat`](https://linux.die.net/man/1/pidstat) из пакета `sysstat` показывает статистику использования ресурсов процессами.

```bash
# I/O статистика для всех процессов
pidstat -d 1

# Для конкретного процесса
pidstat -d -p <PID> 1
```

#### 4.5. Проверка на уровне файловой системы

**Использование [inode](https://ru.wikipedia.org/wiki/Inode):**
```bash
df -i  # Проверка использования inode
```

**Проверка открытых файлов:**
```bash
lsof | wc -l              # Общее количество открытых файлов
lsof /path/to/mount       # Файлы на конкретной файловой системе
cat /proc/sys/fs/file-nr  # Открытые файловые дескрипторы системы
```

#### 4.6. Специфичные для систем хранения инструменты

**Для [LVM](https://ru.wikipedia.org/wiki/LVM):**
```bash
lvs -o +lv_read_ahead,lv_kernel_read_ahead
dmsetup status
```

**Для RAID:**
```bash
cat /proc/mdstat           # Программный RAID
megacli -LDInfo -Lall -aALL  # Для аппаратного RAID (адаптеры LSI/Avago)
```

**Для [NFS](https://ru.wikipedia.org/wiki/Network_File_System):**
```bash
nfsiostat                  # I/O статистика для NFS
nfsstat -c                 # Статистика NFS клиента
```

### 5. Комплексный подход к оценке нагрузки

Для полной картины необходим многоуровневый анализ:

**Уровень 1 - Быстрая диагностика:**
```bash
# Текущее состояние дисков
iostat -x 1 5

# Текущие I/O процессы
sudo iotop -o

# Проверка свободного места
df -h
```

**Уровень 2 - Детальный анализ:**
```bash
# Исторические данные
sar -d

# Процессы с деталями
pidstat -d 1

# Проверка очередей и планировщика
cat /sys/block/sda/queue/scheduler
cat /sys/block/sda/queue/nr_requests
```

**Уровень 3 - Углубленная диагностика:**
```bash
# Трассировка I/O операций
sudo blktrace -d /dev/sda -o trace &
sleep 60
killall blktrace
blkparse -i trace > trace.txt

# Анализ системных вызовов конкретного процесса
sudo strace -e trace=read,write,open,close -p <PID>

# Профилирование с помощью perf
sudo perf record -e block:* -a sleep 30
sudo perf report
```

### 6. Интерпретация результатов

**Признаки проблем с производительностью диска:**

| Метрика | Норма | Проблема | Возможная причина |
|---------|-------|----------|-------------------|
| `%util` | < 70% | > 90% | Диск перегружен |
| `await` | < 10 мс (SSD) <br> < 20 мс (HDD) | > 50 мс | Высокая задержка I/O |
| `avgqu-sz` | < 4 | > 10 | Большая очередь запросов |
| `r_await` vs `w_await` | Сопоставимы | Сильный перекос | Несбалансированная нагрузка |

**Важные нюансы:**

1. **SSD vs HDD**: Для [SSD](https://ru.wikipedia.org/wiki/Твердотельный_накопитель) нормальные значения `await` должны быть < 10 мс, для [HDD](https://ru.wikipedia.org/wiki/Жёсткий_диск) приемлемы значения до 20-30 мс
2. **Случайный vs последовательный доступ**: [HDD](https://ru.wikipedia.org/wiki/Жёсткий_диск) крайне чувствительны к случайному доступу
3. **RAID конфигурация**: [RAID 5/6](https://ru.wikipedia.org/wiki/RAID) имеет низкую производительность записи из-за вычисления [четности](https://ru.wikipedia.org/wiki/Контроль_чётности)
4. **Виртуализация**: В [виртуальных машинах](https://ru.wikipedia.org/wiki/Виртуальная_машина) метрики могут быть искажены из-за [гипервизора](https://ru.wikipedia.org/wiki/Гипервизор)

### 7. Практический пример диагностики

**Сценарий**: Жалобы на медленную работу [базы данных](https://ru.wikipedia.org/wiki/База_данных).

**Шаг 1 - Проверка общей нагрузки:**
```bash
iostat -x 1 5
```
Результат: `%util` для `/dev/sda` - 98%, `await` - 85 мс

**Шаг 2 - Выявление процессов:**
```bash
sudo iotop -o
```
Результат: Процесс `mysqld` генерирует 90% дисковой нагрузки

**Шаг 3 - Анализ типа операций:**
```bash
pidstat -d -p $(pgrep mysqld) 1
```
Результат: Преобладают операции записи (60% write, 40% read)

**Шаг 4 - Проверка конфигурации диска:**
```bash
cat /sys/block/sda/queue/scheduler
cat /sys/block/sda/queue/rotational
```
Результат: Используется планировщик `cfq`, диск - [HDD](https://ru.wikipedia.org/wiki/Жёсткий_диск) (rotational=1)

**Выводы:**
- База данных создает высокую нагрузку на запись
- [HDD](https://ru.wikipedia.org/wiki/Жёсткий_диск) не справляется с нагрузкой
- Рекомендации: миграция на [SSD](https://ru.wikipedia.org/wiki/Твердотельный_накопитель), оптимизация запросов БД, настройка кэширования

### 8. Мониторинг и алертинг

Для проактивного управления производительностью необходим постоянный мониторинг:

**Системы мониторинга:**
- [Prometheus](https://ru.wikipedia.org/wiki/Prometheus_(программное_обеспечение)) + [node_exporter](https://github.com/prometheus/node_exporter) для сбора метрик
- [Grafana](https://ru.wikipedia.org/wiki/Grafana) для визуализации
- [Zabbix](https://ru.wikipedia.org/wiki/Zabbix) для комплексного мониторинга
- [Netdata](https://www.netdata.cloud/) для мониторинга в реальном времени

**Ключевые метрики для алертов:**
- `%util > 80%` в течение 5 минут
- `await > 50 ms` для SSD или `> 100 ms` для HDD
- `avgqu-sz > 8` стабильно
- Rapid growth в количестве операций I/O

### Заключение

Команда `iostat -x` является **базовым, но недостаточным** инструментом для полной оценки нагрузки на диск. Для комплексного анализа необходимо:

1. ✓ Использовать `iostat -x` для первичной диагностики
2. ✓ Применять `iotop` для выявления процессов-источников нагрузки
3. ✓ Использовать `blktrace` для детального анализа I/O паттернов
4. ✓ Анализировать исторические данные с помощью `sar`
5. ✓ Проверять конфигурацию системы хранения (RAID, LVM, планировщики)
6. ✓ Учитывать тип дисков (SSD vs HDD) при интерпретации результатов
7. ✓ Внедрить систему постоянного мониторинга для проактивного управления

Только комплексный подход с использованием множества инструментов позволяет получить реальное представление о нагрузке на дисковую подсистему и выявить узкие места в производительности.
