# Вопрос

На сервере закончилось свободное место, новые файлы не создаются, вывод `df -h` показывает что свободное место есть. Опишите причины по которым такое могло произойти?

[English version](index.md) | [Все вопросы](../../README.ru.md)

---

## Краткий ответ

Наиболее частая причина — исчерпание [inode](https://ru.wikipedia.org/wiki/Inode) (метаданных файлов в файловой системе), когда файловая система исчерпала все inode, хотя дисковое пространство еще доступно. Другие возможные причины: зарезервированное пространство для root, квоты файловой системы, монтирование в режиме только для чтения или проблемы с лимитами конкретных директорий.

---

## Подробное объяснение

Когда `df -h` показывает доступное дисковое пространство, но создание файлов завершается ошибкой, эта парадоксальная ситуация обычно указывает на проблемы, выходящие за рамки простой нехватки места на диске.

### 1. Исчерпание inode (наиболее частая причина)

**Что такое inode?**

[Inode](https://ru.wikipedia.org/wiki/Inode) — это структуры данных в [Unix-подобных файловых системах](https://ru.wikipedia.org/wiki/Файловая_система_Unix), которые хранят метаданные о файлах (права доступа, владельца, временные метки, указатели на блоки данных). Каждому файлу или директории требуется ровно один inode, независимо от его размера.

**Проблема:** Файловая система имеет фиксированное количество inode, выделяемое при создании. Когда все inode использованы, новые файлы создать нельзя, даже если дисковое пространство еще есть.

**Диагностика:**

```bash
# Проверка использования inode
df -i

# Ожидаемый вывод при исчерпании inode:
# Filesystem      Inodes  IUsed   IFree IUse% Mounted on
# /dev/sda1      6553600 6553600     0  100% /
```

**Поиск виновника:**

```bash
# Найти директории с наибольшим количеством файлов
for dir in /*; do
    echo -n "$dir: "
    find "$dir" -type f 2>/dev/null | wc -l
done

# Более детальный поиск в конкретной директории
find /var -type d -exec sh -c 'echo "$(find "{}" -maxdepth 1 | wc -l) {}"' \; 2>/dev/null | sort -rn | head -20

# Найти директории с огромным количеством мелких файлов
du -h --max-depth=2 / 2>/dev/null | grep -E '^[0-9]+K'
```

**Типичные виновники:**

- Лог-файлы в `/var/log` (особенно при неправильной настройке logrotate)
- [Временные файлы](https://ru.wikipedia.org/wiki/Временный_файл) в `/tmp` или `/var/tmp`
- Файлы [кэша](https://ru.wikipedia.org/wiki/Кэш) (кэш браузеров, кэш приложений)
- Очереди писем в `/var/spool/mail`
- Файлы сессий в `/var/lib/php/sessions` или подобных
- Репозитории [Git](https://ru.wikipedia.org/wiki/Git) с множеством мелких объектов
- Директории `node_modules` в проектах [Node.js](https://ru.wikipedia.org/wiki/Node.js)

**Решение:**

```bash
# Удалить ненужные файлы
rm -rf /var/log/old-logs/*
rm -rf /tmp/*
rm -rf /var/tmp/*

# Очистить кэши пакетных менеджеров
apt-get clean  # Debian/Ubuntu
yum clean all  # RedHat/CentOS

# Найти и удалить пустые файлы
find /var -type f -empty -delete

# Проверить восстановление inode
df -i
```

**Профилактика:**

```bash
# Создать файловую систему с большим количеством inode
mkfs.ext4 -N 20000000 /dev/sdb1  # Указать количество inode

# Или увеличить соотношение байт-на-inode (больше inode)
mkfs.ext4 -i 4096 /dev/sdb1  # Один inode на 4KB (по умолчанию часто 16KB)
```

### 2. Зарезервированные блоки для root

**Проблема:** [Файловые системы Ext](https://ru.wikipedia.org/wiki/Ext4) по умолчанию резервируют 5% пространства для [суперпользователя root](https://ru.wikipedia.org/wiki/Суперпользователь), чтобы предотвратить сбой системы при заполнении диска. Обычные пользователи не могут использовать это зарезервированное пространство.

**Диагностика:**

```bash
# Проверить зарезервированные блоки
df -h    # Показывает доступное пространство для обычных пользователей
df -lh   # Показывает общее пространство
tune2fs -l /dev/sda1 | grep -i reserved

# Ожидаемый вывод:
# Reserved block count:     327680
# Reserved blocks uid:      0 (user root)
# Reserved blocks gid:      0 (group root)
```

**Проверка:**

```bash
# Обычный пользователь видит "нет места"
touch /testfile
# Ошибка: No space left on device

# Root все еще может создавать файлы
sudo touch /testfile
# Успех
```

**Решение:**

```bash
# Уменьшить зарезервированное пространство (использовать осторожно!)
# Уменьшить с 5% до 2% на не-системных разделах
sudo tune2fs -m 2 /dev/sda1

# Для разделов только с данными (не /, /var, /usr), можно уменьшить до 0%
sudo tune2fs -m 0 /dev/sdb1

# Проверить изменение
sudo tune2fs -l /dev/sda1 | grep -i "reserved"
```

### 3. Дисковые квоты

**Проблема:** [Дисковые квоты](https://ru.wikipedia.org/wiki/Квота_(информатика)) могут ограничивать конкретных пользователей или группы, даже когда в системе есть доступное пространство.

**Диагностика:**

```bash
# Проверить, включены ли квоты
mount | grep quota
cat /etc/fstab | grep quota

# Проверить квоту пользователя
quota -v
repquota -a

# Проверить детали квоты
quota -u username
```

**Решение:**

```bash
# Увеличить квоту пользователя (требуется root)
edquota -u username

# Или временно отключить квоты
quotaoff -a

# Повторно включить квоты
quotaon -a
```

### 4. Файловая система только для чтения

**Проблема:** Файловая система смонтирована в режиме [только для чтения](https://ru.wikipedia.org/wiki/Защита_от_записи) из-за ошибок или намеренной конфигурации.

**Диагностика:**

```bash
# Проверить опции монтирования
mount | grep "ro,"
cat /proc/mounts | grep "ro,"

# Проверить ошибки файловой системы в логах
dmesg | grep -i "read-only"
journalctl -xe | grep -i "read-only"
```

**Решение:**

```bash
# Перемонтировать в режиме чтения-записи
mount -o remount,rw /

# Если в файловой системе есть ошибки, проверить и исправить
umount /dev/sda1
fsck -y /dev/sda1
mount /dev/sda1
```

### 5. Лимиты файловых дескрипторов

**Проблема:** Достигнуты системные или процессные лимиты [файловых дескрипторов](https://ru.wikipedia.org/wiki/Файловый_дескриптор).

**Диагностика:**

```bash
# Проверить текущие лимиты
ulimit -n   # Текущий shell
cat /proc/sys/fs/file-max   # Общесистемный максимум
cat /proc/sys/fs/file-nr    # Текущие открытые файлы

# Проверить лимиты для процесса
lsof | wc -l
lsof -u username | wc -l
```

**Решение:**

```bash
# Увеличить лимиты временно
ulimit -n 65536

# Постоянное изменение в /etc/security/limits.conf
echo "* soft nofile 65536" >> /etc/security/limits.conf
echo "* hard nofile 65536" >> /etc/security/limits.conf

# Общесистемный лимит
echo "fs.file-max = 2097152" >> /etc/sysctl.conf
sysctl -p
```

### 6. Плохие блоки или повреждение файловой системы

**Проблема:** [Повреждение файловой системы](https://ru.wikipedia.org/wiki/Фрагментация_(компьютер)) или [плохие блоки](https://ru.wikipedia.org/wiki/Сбойный_сектор), препятствующие записи.

**Диагностика:**

```bash
# Проверить ошибки файловой системы
dmesg | grep -i error
journalctl -xe | grep -i "I/O error"

# Проверить плохие блоки
badblocks -v /dev/sda1

# Проверка файловой системы
umount /dev/sda1
fsck -n /dev/sda1  # Неразрушающая проверка
```

**Решение:**

```bash
# Восстановить файловую систему
umount /dev/sda1
fsck -y /dev/sda1

# При серьезном повреждении - резервное копирование и пересоздание
```

### 7. Ограничения SELinux или AppArmor

**Проблема:** [Политики безопасности](https://ru.wikipedia.org/wiki/SELinux), препятствующие созданию файлов.

**Диагностика:**

```bash
# Проверить статус SELinux
getenforce
sestatus

# Проверить отказы
ausearch -m avc -ts recent
grep "denied" /var/log/audit/audit.log

# AppArmor
aa-status
dmesg | grep -i apparmor
```

**Решение:**

```bash
# Временно отключить (только для тестирования!)
setenforce 0  # SELinux
systemctl stop apparmor  # AppArmor

# Лучше: исправить политику или контекст
chcon -R -t proper_type /path
restorecon -R /path
```

### 8. Лимиты записей в директории

**Проблема:** Некоторые файловые системы имеют ограничения на количество записей в директории (хотя это редкость в современных системах).

**Диагностика:**

```bash
# Проверить количество файлов в директории
ls -la | wc -l

# Для ext3/ext4 проверить функцию dir_index
tune2fs -l /dev/sda1 | grep dir_index
```

**Решение:**

```bash
# Включить dir_index для лучшей обработки больших директорий
tune2fs -O dir_index /dev/sda1
e2fsck -D /dev/sda1  # Оптимизировать директории
```

### 9. Заполнен конкретный раздел или точка монтирования

**Проблема:** Запись идет в неправильный раздел, который на самом деле заполнен.

**Диагностика:**

```bash
# Проверить все смонтированные файловые системы
df -h
df -h /path/to/target/directory

# Узнать, к какой файловой системе относится путь
df -h $(dirname /path/to/file)

# Проверить точки монтирования
mount | column -t
lsblk
```

### Алгоритм диагностики

**Шаг 1: Проверить базовое использование диска**
```bash
df -h     # Использование пространства
df -i     # Использование inode
```

**Шаг 2: Проверить статус монтирования**
```bash
mount | grep $(df /path | tail -1 | awk '{print $1}')
```

**Шаг 3: Проверить права доступа и квоты**
```bash
quota -v
sudo touch /testfile  # Тест от имени root
```

**Шаг 4: Проверить системные логи**
```bash
dmesg | tail -50
journalctl -xe
grep -i "error\|fail" /var/log/syslog
```

**Шаг 5: Протестировать создание файла с подробным выводом ошибок**
```bash
strace touch /testfile 2>&1 | grep -i "error\|fail"
```

### Полный чек-лист для устранения проблемы

1. ✓ Проверить использование inode: `df -i`
2. ✓ Проверить зарезервированные блоки: `tune2fs -l /dev/sda1`
3. ✓ Проверить дисковые квоты: `quota -v`
4. ✓ Убедиться, что файловая система доступна для записи: `mount | grep ro`
5. ✓ Проверить лимиты файловых дескрипторов: `ulimit -a`
6. ✓ Просмотреть системные логи: `dmesg` и `journalctl`
7. ✓ Протестировать с правами root: `sudo touch /testfile`
8. ✓ Проверить SELinux/AppArmor: `getenforce`, `aa-status`
9. ✓ Проверить правильность раздела: `df -h /path`
10. ✓ Проверить целостность файловой системы: `fsck -n /dev/sda1`

### Профилактика и мониторинг

**Настроить мониторинг:**

```bash
# Проверка Nagios/Icinga
check_disk -w 20% -c 10% -W 20% -K 10%  # Предупреждать о пространстве И использовании inode

# Prometheus node_exporter предоставляет метрики:
# - node_filesystem_avail_bytes
# - node_filesystem_files (всего inode)
# - node_filesystem_files_free

# Простой скрипт мониторинга
cat > /usr/local/bin/check_inodes.sh << 'EOF'
#!/bin/bash
THRESHOLD=90
df -i | awk 'NR>1 {gsub("%","",$5); if($5>threshold) print $1" использование inode: "$5"%"}' threshold=$THRESHOLD
EOF
chmod +x /usr/local/bin/check_inodes.sh

# Добавить в crontab
echo "0 * * * * /usr/local/bin/check_inodes.sh" | crontab -
```

**Лучшие практики:**

- Мониторить И дисковое пространство, И использование inode
- Настроить алерты на уровнях 80% и 90%
- Внедрить ротацию логов ([logrotate](https://linux.die.net/man/8/logrotate))
- Регулярно очищать временные файлы
- Архивировать старые логи вместо удаления
- Использовать отдельные разделы для `/var`, `/tmp`, `/home`
- При создании файловых систем оценивать количество файлов и настраивать соотношение inode

### Сводка полезных команд

```bash
# Диагностика
df -h                           # Дисковое пространство
df -i                           # Использование inode
df -Th                          # Включая тип файловой системы
mount | grep ro                 # Монтирования только для чтения
tune2fs -l /dev/sda1            # Параметры файловой системы
quota -v                        # Квоты пользователя
lsof | wc -l                    # Количество открытых файлов
dmesg | tail                    # Системные сообщения

# Поиск больших потребителей
du -sh /*                       # Размеры директорий верхнего уровня
find / -type f -size +100M      # Большие файлы
find / -type f | wc -l          # Общее количество файлов
find / -xdev -type f | cut -d "/" -f 2 | sort | uniq -c | sort -rn  # Файлов в каждой директории верхнего уровня

# Очистка
apt-get autoclean               # Очистить кэш пакетов
journalctl --vacuum-time=7d     # Очистить старые журналы
find /tmp -type f -atime +7 -delete  # Старые временные файлы
find /var/log -name "*.gz" -delete   # Сжатые старые логи
```
